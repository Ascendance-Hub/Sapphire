# Pre-1.0 API decisions — design

Date: 2026-05-16 · Branch: `season-five/fix-review-bugs`

## Context

The season-five code review (`specs/v1/season-five/CODE_REVIEW.md`) flagged four
findings that are not bugs but **public-API behaviour** — once a stable 1.0
ships they become breaking to change. This spec records the decisions taken for
each and the implementation approach. The four bugs (B1–B4), S6 and S7 are
already handled on this branch; this spec covers S1, S2, S5, I4.

| #  | Finding                                              | Decision                                  |
| -- | ---------------------------------------------------- | ----------------------------------------- |
| S1 | `adapterRegistry` is module-global mutable state     | Keep global; document it.                 |
| S2 | Absent optional keys materialize as `undefined`      | Omit them from the output (Zod-like).      |
| S5 | `.url()` accepts any URL scheme                      | Default to `http`/`https`; make it configurable. |
| I4 | `SapphireSchemaNode.message` declared, never emitted | Remove it from the IR type.               |

S2 and S5 are observable behaviour changes — they ship under one `minor`
changeset (the `fixed` group bumps all five packages together). All changes are
implemented test-first (RED verified before GREEN), consistent with B1–B4.

---

## S1 — keep the global adapter registry

### Decision

The registry stays a module-global `Map` in `packages/core/src/adapters/registry.ts`.
`registerAdapter` / `getSchema(name)` are unchanged. Registering one adapter
never blocks another — multiple adapters coexist under distinct keys, which is
the whole "schema once, adapters everywhere" premise. Global vs per-instance
only affects the rare case of two `Sapphire` instances needing *different*
adapter sets in one process; that is YAGNI for the target use case.

### Implementation

- No code change.
- Add a doc-comment to `adapters/registry.ts` stating the registry is process-
  global and adapters should be registered once at application startup.
- Add a short note to the docs (the `custom-adapter` recipe and/or
  `getting-started`) making the "register once at startup" contract explicit,
  in both `docs/` and `docs/pt-br/`.

### Test impact

None.

## S2 — omit absent optional keys from parse output

### Problem

`ObjectField._parse` sets `out[key] = sub.value` for **every** declared key. An
optional key absent from the input yields `sub.value === undefined`, so the key
still appears in the output:

```ts
a.object({ nickname: a.string().optional() }).parse({})
// current → { nickname: undefined }   ('nickname' in result === true)
```

This diverges from Zod (which omits the key) and from Sapphire's own `Infer`
type, which already types the key as optional (`nickname?: string`).

### Decision

Omit an optional key from the output when it was absent from the input. Match
Zod's nuance: a key passed *explicitly* as `undefined` is preserved.

```ts
a.object({ nickname: a.string().optional() }).parse({})
// new → {}
a.object({ nickname: a.string().optional() }).parse({ nickname: undefined })
// new → { nickname: undefined }   (explicit undefined preserved)
```

### Implementation

`packages/core/src/core/object.ts`, the per-key loop in `_parse`. Issues are
still pushed unconditionally; only the assignment to `out` is gated:

```ts
const sub = (child as unknown as InternalField)._parse(v[key], childCtx)
if (key in v || sub.value !== undefined) {
  out[key] = sub.value
}
issues.push(...sub.issues)
```

Rationale for the gate:
- `key in v` true → input carried the key; preserve it (incl. explicit `undefined`).
- `sub.value !== undefined` true → a value was produced (e.g. a `default`
  filled in); keep it even though the key was absent from input.
- Both false → optional key, absent, no default → omit.

A required key that is absent still produces its `required` issue; its value is
discarded with the rest of the failed parse, so omitting it from `out` is
harmless.

### Test impact

Medium. Any test asserting object equality with an explicit `undefined` optional
key (`toEqual({ ..., opt: undefined })`) must drop that key. Property *access*
(`result.opt`) still yields `undefined`, so only literal `toEqual` assertions
break. Sweep `packages/core/tests/{fields,validation,docs-examples}` and
`packages/core/tests/multi-adapter`, plus adapter tests, and update. Add a
dedicated regression test (`tests/bugs/optional-key-omitted.test.ts`) covering:
absent → omitted, explicit `undefined` → preserved, `default` → present,
`nullable` `null` → present.

## S5 — `.url()` defaults to http/https, protocols configurable

### Problem

`.url()` validates with `new URL(v)` in a try/catch, which accepts any valid
scheme — `javascript:`, `data:`, `file:`, `mailto:`, `foo:bar`. The 99% use of
`.url()` is a web link, and `javascript:` passing is a mild XSS footgun.

### Decision

`.url()` defaults to accepting only `http` and `https`. A `protocols` option
widens it:

```ts
a.string().url()                                  // http, https
a.string().url({ protocols: ['http', 'https', 'ftp'] })
a.string().url({ protocols: ['mailto'] })
```

### Implementation

Default protocol list lives in one place:

```ts
// format-validators.ts
export const DEFAULT_URL_PROTOCOLS = ['http', 'https']

export function isUrl(v: string, protocols: readonly string[]): boolean {
  try {
    const u = new URL(v)
    return protocols.includes(u.protocol.slice(0, -1)) // 'http:' → 'http'
  } catch {
    return false
  }
}
```

- `formatValidators.url` becomes `(v) => isUrl(v, DEFAULT_URL_PROTOCOLS)` — the
  exported validator's default narrows to http/https (signature unchanged).
- `isUrl` and `DEFAULT_URL_PROTOCOLS` are exported from `@ascendance-hub/sapphire-core`.
- `StringField.url(opts?)` — `opts` gains `protocols?: string[]`; stored as
  `config.urlProtocols`.
- `StringConfig` and the `string` IR node gain `urlProtocols?: string[]`.
  `toSchema()` emits `urlProtocols` whenever `format === 'url'`, with the value
  resolved to `config.urlProtocols ?? DEFAULT_URL_PROTOCOLS` — so the IR is
  self-contained and adapters need no default of their own.
- `StringField._parse` — the format check special-cases `url`:
  `format === 'url' ? isUrl(str, config.urlProtocols ?? DEFAULT_URL_PROTOCOLS)
  : formatValidators[format](str)`.
- **Mongoose adapter** — the `url` validator is built from `node.urlProtocols`:
  `{ validator: (v) => isUrl(v, node.urlProtocols ?? DEFAULT_URL_PROTOCOLS),
  message: 'Invalid url' }`.
- **JSON Schema adapter** — keeps emitting `format: 'uri'`. JSON Schema `format`
  has no protocol-restricted variant; the protocol list is a documented gap
  there (core- and Mongoose-enforced), like BSON. No change.
- **BSON adapter** — `url` already has no `$jsonSchema` equivalent (enforced
  client-side). No change.

### Test impact

Medium. Existing `.url()` tests using `http`/`https` URLs still pass. Tests
asserting a non-http URL passes `.url()` must add `{ protocols: [...] }` or move
to a regex. Sweep `packages/core/tests/fields/string.test.ts`,
`packages/mongoose/tests/mongoose.string-format.test.ts`, the json-schema tests,
and `docs-examples`. Add a regression test covering: http/https pass by default,
`javascript:`/`mailto:` rejected by default, `protocols` widens, IR carries
`urlProtocols`.

## I4 — remove `SapphireSchemaNode.message`

### Problem

`NodeBase` (`packages/core/src/schema/types.ts`) declares `message?: FieldMessages`,
but no `toSchema()` ever emits it — `fieldMessage` config stays internal to the
parse runtime. It is dead surface in an exported public type; a custom-adapter
author could code against `node.message` and always read `undefined`.

### Decision

Remove `message` from `NodeBase`. Re-adding an optional IR field later is
non-breaking, so nothing is lost.

### Implementation

- Delete `message?: FieldMessages` from `NodeBase` in `schema/types.ts`.
- Remove the now-orphaned `import type { FieldMessages }` from that file
  (`NodeBase.message` is its only use).

### Test impact

None expected. `tsc --noEmit` confirms nothing reads the field.
